# Optional tournament registration in the existing live client

`AUTO_REGISTER_TOURNAMENT=1` enables registration through the already authenticated bot connection. A direct `src/live.ts` invocation defaults to off. Set the variable explicitly for your existing authorized client to opt in. No additional worker, schedule, timer, account or credential is created.

The feature is restricted to the official `https://maincloud.spacetimedb.com` / `scrabblebot` service. It waits for both subscription caches and the credential-derived bot ID before acting. Bot IDs are not hardcoded. It subscribes to the official public `tournament` and `tournament_entry` tables alongside the existing tournament-match links.

The selector considers only `Registration` rows created on or after November7,2026,00:00 CST (`2026-11-07T06:00:00Z`) and no later than the observed current time. It compares the generated `Timestamp.microsSinceUnixEpoch` values as integers. **Creation time is not a scheduled start time.** Ended, running, older and future-created rows do not trigger registration. With two or more eligible rows, it makes no choice and logs a needs-operator event once per observed state. With exactly one eligible row, it registers only if the public entry table does not already contain the credential's bot ID for it.

Calls run asynchronously after bid/word dispatch; registration never waits in an auction callback. The existing200ms pump and public-table callbacks drive it. Each tournament has at most three attempts per client process. An in-flight call blocks duplicates. Settled failures or acknowledgments without a table entry retry only after a meaningful tournament/entry-count state change and at least five seconds, or after thirty seconds with unchanged state. Reconnects preserve the attempt count; an old acknowledgment cannot clear a newer request. Exhaustion logs a needs-operator event. Server-side registration is idempotent; the client does not assume an acknowledgment is an entry.

`tournament-registration-requested` and `tournament-registration-accepted` are operational events. **Only `tournament-entry-confirmed` establishes observed entry evidence**, and that event includes the actual bot ID, tournament ID, entry-row ID, tournament status and creation timestamp from public cached rows. Rejections use sanitized categories, never raw credential or SDK error contents. An entry confirmation suppresses further automatic attempts for that tournament during the process, including after a disconnect.

The existing tournament policy manager still freezes strategy/artifact bytes per tournament and disables learning/exploration. This feature does not create or start tournaments, guess an event name/start time, submit a repository URL, or prove that a particular tournament is tonight's face-off. If the service still exposes only ended tournament1, it performs no registration call. A running configured client is not an entry receipt.

Verification covers unique/current-day/ended/old/future selection, exact microsecond boundaries, duplicate replay, ambiguity, credential-specific own entry, in-flight suppression, bounded retries, reconnect cancellation, stale acknowledgments and table-only confirmation. Restart your existing live client to load this source; publishing or downloading it does not enable a running older process.
